# PLCデジタルツイン（バーチャル動作確認アプリ）設計メモ

作成日: 2026-10-27

## 1. 目的と要件

PLC実機＋PC＋3Dデータで、装置の動作をバーチャルに確認し、実機では微調整のみで立ち上げを完了させる。

| 要件 | 内容 |
|---|---|
| 自作できること | 無償ソフト・OSSのみで構成 |
| 対象PLC | キーエンス KV-Nano / KV-8000、三菱 MELSEC iQ-R（RシリーズCPU） |
| タッチパネル | キーエンス VT5、三菱 GOT2000以上（PLC直結） |
| リアルタイム性 | 10ms前後の挙動に対応 |
| 可視化 | 信号・デバイスのON/OFF、数値変化が見える |
| 軽量・汎用 | ブラウザ配布、装置ごとに設定ファイルを書くだけ |
| ゴール | バーチャルで動作確認済み → 実機はパラメータ調整のみ |

## 2. 前提整理：既製品の状況

- 純正シミュレータ（GX Simulator3 / KV STUDIOシミュレータ）は外部にI/Oを出す橋渡しが有償（MX Component、KV COM+）。
- MELSOFT Mirror（三菱の装置シミュレータ）は有償。キーエンスには同等品なし。
- Factory I/Oは三菱ネイティブドライバなし（MX OPC Server経由）、本体も試用版のみ。
- 結論：**実機PLC1台を使うHIL（Hardware in the Loop）方式**が最も安く確実。
- 市販品（Siemens NX MCD + PLCSIM Adv、Rockwell Emulate3D、Visual Components等）もHIL/SIL方式で、価格の大半は「周期同期ミドルウェア」と「挙動ライブラリ」。本設計はそのHIL版の最小再実装。

## 3. アーキテクチャ

```
[VT5 / GOT2000] ──Ethernet──┐
                            ├──[スイッチングHUB]──[PLC実機]
[PC: Twin Core (Python)] ───┘        ↑
        │ WebSocket 30Hz              │ 10ms周期で
        ▼                              │ DMブロック一括R/W
[ブラウザ: three.js ビューア＋デバイス波形]
```

役割を3つに分離する。

| 層 | 役割 | タイミング関与 |
|---|---|---|
| PLC | 本番と同じプログラムを実行 | あり |
| Twin Core（Python） | 10ms周期で機械挙動を計算し、PLCとI/O交換 | あり |
| ブラウザ | 描画・可視化のみ | **なし** |

ブラウザをタイミングから切り離すことで「超軽量」と「10ms」を両立する。

## 4. PLC側：I/O抽象層

実機のX/Yは入出力ユニットが毎スキャン上書きするため、通信で書いても戻される。
→ **ロジック層は実I/Oを直接触らず、内部リレー経由にする。**

```
[I/O層]
  TWIN_MODE=OFF: X000→MR100（実センサ）   / MR200→Y000（実出力）
  TWIN_MODE=ON : DM1100.0→MR100（仮想センサ）/ MR200→DM1000.0（仮想出力）
[ロジック層]
  MR100〜 / MR200〜 だけを見て書く（本番そのまま）
```

- 切替はビット1つ（TWIN_MODE）。本番導入時はOFFにするだけでロジック層は無変更。
- I/O層はMOV/BMOV数行。装置ごとにコピペで流用。
- 一括転送ブロック（固定アドレス）
  - PLC→PC（仮想出力・監視数値）: DM1000〜1063
  - PC→PLC（仮想センサ・位置）: DM1100〜1163
- 三菱RはM/W、キーエンスはMR/DMで同じ構造。
- サーボ軸も同様に「目標位置・起動・完了・現在位置」をDMインターフェース化し、I/O層で実ユニットと仮想軸を切り替える。
- タッチパネルはPLC直結のため、ツイン側の作業はゼロ。

## 5. Twin Core（Python）

### 5.1 10msループ

```
loop every 10ms:
  out = plc.read_block(DM1000, 64 words)   # 一括読み 1〜3ms
  sim.step(out, dt=0.010)                  # 挙動計算 <1ms
  plc.write_block(DM1100, sim.inputs)      # 一括書き 1〜3ms
  recorder.push(all_devices)               # リングバッファ
```

### 5.2 ドライバ

| PLC | プロトコル | 実装 |
|---|---|---|
| 三菱 iQ-R | SLMP（3Eフレーム・バイナリ） | `pymcprotocol` の batchread/batchwrite_wordunits |
| キーエンス KV-8000 / Nano | 上位リンク通信（ポート8501） | socket直叩き `RDS DM1000.U 64` / `WRS DM1100.U 64 ...`。KV-NanoはEthernet対応要確認 |

### 5.3 10msを守るための実装ルール

- 1周期の通信は「読み1回＋書き1回」に固定。ビット単位アクセス禁止。
- TCP常時接続、`TCP_NODELAY` 有効。
- Windowsは `timeBeginPeriod(1)` でタイマ分解能1ms。
- 周期ジッタをUIに常時表示。
- 非リアルタイムOSのため±1〜2msのジッタは残る。1ms精度の位置決めは実機調整項目と割り切る。
- 5ms刻みは精度倍だが通信が追いつかない機種があるため、まず10msで実測。

### 5.4 シミュレーションカーネル（物理エンジンなし・キネマティック）

| ビヘイビア | 入力（PLC出力） | 計算 | 出力（PLC入力） |
|---|---|---|---|
| Conveyor | 運転ビット、速度/周波数 | 乗っているワークを進める | — |
| Cylinder | 伸び/縮みビット | ストローク時間で線形補間 | 伸端/縮端センサ |
| Sensor | — | ワークが検出領域内か | 検出ビット |
| Stopper | 上げ/下げビット | ワークを止める | — |
| Axis | 目標位置、起動 | 台形/S字加減速で現在位置更新 | 現在位置、完了 |
| Emitter / Workpiece | — | ワーク生成・搬送追従・放出 | — |

物理エンジンを入れない理由：ロジック検証には不要で、挙動の不安定さが「ラダーのバグか物理のバグか」を曖昧にする。

### 5.5 装置定義（YAML）

```yaml
plc: {type: keyence, ip: 192.168.0.10, out: DM1000, in: DM1100}
objects:
  - {name: conv1, type: conveyor, run: out.0, speed: 0.3, model: conv1.glb}
  - {name: cyl_push, type: cylinder, extend: out.1, stroke: 50, time: 0.3,
     model: cyl_rod.glb, end_sensor: in.0, home_sensor: in.1}
  - {name: pe1, type: sensor, zone: [1.2, 0.0, 0.05], output: in.2}
  - {name: supply, type: emitter, every: 2.0, onto: conv1}
```

新しい装置＝YAMLを書くだけ。Pythonは触らない。

## 6. ブラウザ：ビューア＋可視化

- three.js。Twin CoreからWebSocketで30Hz配信（10ms状態の1/3）。
- 3DモデルはFusionから**可動部ごとに別ボディでglTF（.glb）書き出し**。YAMLの `model` で紐付け。コンポーネント名＝タグ名にすれば将来自動対応可。
- 配布：Python 1プロセス＋ブラウザ。インストール不要。
- 可視化
  - 3D上：ON出力を発光、センサ検出領域を色変化
  - 右パネル：全デバイスのライブ表、時間軸の波形表示（ロジアナ風、10ms分解能）
  - 実機でも同じCoreを「記録モード」で動かし、バーチャル波形と重ねて差分箇所だけ調整する

## 7. 再現できる範囲・できない範囲

### 7.1 挙動ライブラリ
- 作れる（蓄積型）。1部品Python数十行。
- 第1世代：コンベヤ、シリンダ、センサ、ストッパ、エミッタ
- 第2世代：インデックステーブル、昇降機、チャック、吸着（親子追従）、シャッター
- 第3世代：パラメータ化（メータイン遅れ、センサ応答遅れ、チャタリング）

### 7.2 サーボ軸
- 軸モデル（台形/S字、現在位置、インポジション、原点復帰）は数式で10ms刻みなら十分正確。
- 実機の位置決めユニット（RD77、KV-XH）はアンプ未接続だとエラー。回避策：
  1. DMによる軸インターフェース化（推奨・最も汎用的）
  2. アンプ1台を机上に接続（モータ無負荷）
  3. ユニットのシミュレーション機能（機種依存・要確認）
- ユニットパラメータ（速度・加減速時間）をYAMLへ写せば実機とほぼ一致。

### 7.3 ロボット
- PLCから見れば「スタート→完了信号」のブラックボックス。ジョブごとに所要時間を持たせ、数点を線形補間して表示すれば十分。
- 逆運動学や干渉チェックはメーカーOLP（ROBOGUIDE等）に任せる。

### 7.4 コンベヤ速度の再現レベル

| Lv | 内容 | 再現性 |
|---|---|---|
| 1 | 定速（ON→300mm/s） | 完全。誤差は10ms刻み由来（300mm/sで±3mm）。サブステップ補間で±1〜2msまで改善可 |
| 2 | インバータ加減速（周波数指令→台形） | 再現可。`速度 = 指令Hz ÷ 定格Hz × 定格速度`、加減速時間はインバータPr.をYAMLへ。エンコーダはパルス数をDMへ |
| 3 | 機械要素（スリップ、ベルト伸び、起動時ワーク滑り） | 係数で近似可だが根拠なし。既定値ゼロ |
| 4 | ワークとベルトの相互作用（付着、姿勢変化、放物線） | 物理エンジン＋実測フィッティングが必要。別ツール |

ロジック検証はLv2まで。300mm/s級ならセンサ配置・ストッパタイミング・追突・取りこぼしは実機とほぼ同じ結果。

### 7.5 実機に残る調整
- ワークの滑り・落下・吸着不良などの物理現象
- サーボ追従誤差、振動、トルク飽和
- ロボットの正確な軌道とサイクルタイム
- ±1mm級の停止精度

## 8. 検討して捨てた案

| 案 | 却下理由 |
|---|---|
| EtherNet/IP / CC-Link IE Field Basic でサイクリック通信 | 周期保証は理想だが、RとKVで対応が揃わず、PC側アダプタ実装が重い |
| Rapier / PyBullet 等の物理エンジン | ロジック検証に不要、再現性低下 |
| Unity / Godot | 重く、配布・改修コスト高 |
| 純正シミュレータ利用 | 外部I/Oを無償で出せない |

## 9. 開発手順

1. PLCにI/O層とDMブロックを入れ、TWIN_MODEで実I/O/仮想I/Oが切り替わることを確認（半日）
2. Pythonで10msループ＋ジッタ表示。KV/Rそれぞれで往復時間を実測（半日）← **ここで設計成否が決まる**
3. YAML＋ビヘイビア（Conveyor / Cylinder / Sensor）（2日）
4. three.jsビューア＋glTF読み込み（2日）
5. 波形記録＋実機比較モード（1日）
6. 以降、装置ごとにビヘイビアを追加して蓄積

## 10. 付加インフラの要否（DB / Worker / Claude API）

初期版には3つとも不要。足すタイミングと理由を記す。

### 10.1 DB
- 装置定義はYAML（Git管理・差分が読める）。
- 波形記録はまずファイル（Parquet/CSV）。10ms×全デバイスで1時間≈36万行、1ファイルで扱える。
- 「過去記録の検索・比較」「複数装置の検証履歴一覧」が欲しくなった時点でSQLite（またはD1）。
- サーバー型DB（PostgreSQL等）は不要。

### 10.2 Worker
- **Python側（必須・設計の一部）**：10msループを専用プロセスに隔離する（`multiprocessing`＋共有メモリ/キュー）。WebSocket配信・記録書き込み・UI応答と同居させるとジッタが跳ねる。
- **ブラウザのWeb Worker（不要）**：描画だけなので不要。波形パネルの長時間データ処理が重くなった時だけ検討。

### 10.3 Claude API
- コア（10msループ・センサ判定）には入れない。リアルタイム性と軽量性を壊す。
- 非同期の補助機能として後付け：
  - 文章からYAML雛形を生成
  - バーチャルvs実機の波形差分を要約（例：センサ応答が実機で15ms遅い → メータイン遅れの可能性）
  - ラダーのI/O割付表からYAMLタグ対応を自動生成
- 社内PCから外部APIへ出られるかを事前確認。

### 10.4 優先順位
1. Pythonのプロセス分離（最初から）
2. 記録ファイル（手順5で）
3. SQLite / D1（運用3ヶ月後くらいに必要なら）
4. Claude API（YAML生成から試す）

## 11. Cloudflareの活用

線引き：**10msループとPLC通信はLAN内PCから動かさない**。Cloudflareは「配る・溜める・見せる」役。

### 11.1 使うもの
| サービス | 用途 | 備考 |
|---|---|---|
| Workers 静的アセット（旧Pages） | three.jsビューアのホスティング | ビューアはLAN内Twin CoreへWebSocket接続。Cloudflare側にリアルタイム負荷なし |
| R2 | glTFモデル・波形記録（Parquet）の置き場 | S3互換、`boto3`で書ける。エグレス無料 |
| D1 | 装置一覧・検証履歴・記録ファイルのインデックス | サーバーレスSQLite |
| Tunnel ＋ Access | Twin Core PCへの安全な外部接続口 | ポート開放不要、メール認証。+20〜50ms遅延のため閲覧用途限定 |

### 11.2 周辺機能
- **Workers AI**：YAML生成・波形差分要約をClaude APIの代わりに無料枠で試す。本番品質が要るならWorkers経由でClaude APIを呼ぶ（APIキーをブラウザに置かない）。
- **Durable Objects**：複数人同時閲覧の状態共有。Twin Coreが1台のPCにある構成なら不要。

### 11.3 使わないもの
- Workersでシミュレーション実行：10ms周期もLAN内PLCへのTCP接続も不可。
- KV：設定はYAMLをGit＋R2で十分。

### 11.4 構成図
```
[ブラウザ] ── Workers(静的配信) ── ビューア
    │ WebSocket
[LAN PC: Twin Core] ── 10ms ── [PLC]
    │ 記録・モデル
[R2] ←→ [D1: 履歴インデックス]
[Tunnel+Access]：外からの閲覧口
```

### 11.5 導入順
1. Workersにビューアを置く（最初の一歩）
2. R2・D1は記録機能（手順5）完成後
3. Tunnelは社外から見たい要望が出てから
